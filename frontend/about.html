How SARR finds packages

A retrieval stack built for intent — embeddings, vector search, and ranking that mixes meaning with real-world adoption.

The problem

Package registries are easy to search when you already know a name. They are harder when you only know the job: an HTTP client, a dataframe tool, something for retries. Keyword indexes reward exact tokens; they under-serve descriptive queries and rarely encode whether a project is widely used or still maintained.

SARR (Semantic Artifacts Retrieval and Ranking) indexes PyPI packages as semantic documents and returns a ranked list for natural-language queries. The live demo covers on the order of 168k packages drawn from public Libraries.io metadata joined with repository signals.

End-to-end path

  1. Index offline. A GPU batch job pulls PyPI rows from BigQuery, builds a structured text document per package, embeds it with a bi-encoder, and upserts vectors plus metadata into Qdrant. Runs are watermarked so a disconnect can resume without duplicating points.
  2. Encode the query online. The same embedding model used at index time maps your search string into the same vector space — keeping train/serve representation aligned.
  3. Retrieve neighbors. Approximate nearest-neighbor search returns the closest packages by cosine similarity over the full collection.
  4. Refine when needed. An optional cross-encoder rescores a short top‑k list with a deeper query–document model. It is toggled per request so you can trade a bit of latency for precision on harder queries.
  5. Blend for usefulness. The final score mixes semantic relevance with adoption (stars, dependents, SourceRank) and release recency. Popularity stays in structured payload fields so it influences rank without polluting the embedding text.

Compared with PyPI.org search

Typical registry search

  • Strong on exact names and known keywords
  • Struggles when the query is a use-case, not a title
  • Little visibility into “is this still maintained?”

SARR

  • Matches intent in embedding space
  • Handles descriptive queries without exact lexical overlap
  • Surfaces better-maintained, more adopted options when relevance is close

Try “machine learning” or “async HTTP client with retries” on the search page: relevant libraries appear even when those phrases are absent from the package name.

Models and systems choices

The MVP uses a compact bi-encoder (BAAI/bge-small-en-v1.5, 384 dimensions) so indexing ~168k documents on a Colab T4 stays practical, and query embedding on CPU remains acceptable for a demo API. Reranking uses a small cross-encoder on the retrieved shortlist rather than scoring the whole corpus — the usual two-stage IR pattern: cheap recall, then selective precision.

Serving keeps the heavy lift out of the request path: corpus embeddings are precomputed; each request only embeds the query, hits the vector store, and optionally reranks. The API is structured for the same code path locally and in a containerized Lambda image, with shared schemas and document formatting between ETL and search.

What “fast enough” looks like today

  • Full corpus load completed for 167,619 packages (embed + Qdrant upsert).
  • After models are warm, searches commonly land around half a second to a couple of seconds depending on network to Qdrant Cloud and whether rerank is on — with per-stage timings exposed so you can see embed vs retrieval cost.
  • The first request after a process start is slower: weights load once, then stay resident for subsequent queries.
