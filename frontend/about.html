How SARR finds packages

A retrieval stack built for intent — embeddings, vector search, and ranking that mixes meaning with real-world adoption.

The problem

Package registries are easy to search when you already know a name. They are harder when you only know the job: an HTTP client, a dataframe tool, something for retries. Keyword indexes reward exact tokens; they under-serve descriptive queries and rarely encode whether a project is widely used or still maintained.

SARR (Semantic Artifacts Retrieval and Ranking) indexes PyPI packages as semantic documents and returns a ranked list for natural-language queries. The live demo covers 167,619 packages from public Libraries.io metadata joined with repository signals. That dump is an MVP corpus — the newest release timestamp in this slice is from December 2018 — so ranking features are strong, while freshness is a known next step.

System design

Indexing is a rare GPU job (Colab, PyTorch). Serving only embeds the query, retrieves neighbors from Qdrant, optionally reranks, and blends in adoption and recency. On Lambda both the bi-encoder and the cross-encoder run as ONNX — no PyTorch import on the request path. Both paths share the same BAAI/bge-small-en-v1.5 checkpoint and document format.

End-to-end path

  1. Index offline. A GPU batch job pulls PyPI rows from BigQuery, builds a structured text document per package, embeds it with a PyTorch bi-encoder, and upserts vectors plus metadata into Qdrant. Runs are watermarked so a disconnect can resume without duplicating points.
  2. Encode the query online. The same embedding checkpoint used at index time maps your search string into the same 384-d space. Hosted Lambda runs a baked ONNX graph; local dev can still use sentence-transformers when no ONNX files are present.
  3. Retrieve neighbors. Approximate nearest-neighbor search returns the closest packages by cosine similarity over the full collection.
  4. Refine when needed. If you check Rerank, the UI sends rerank: true and an ONNX MiniLM cross-encoder rescores the short top‑k list. No PyTorch import on Lambda.
  5. Blend for usefulness. The final score mixes semantic relevance with adoption (stars, dependents, SourceRank) and release recency. Popularity stays in structured payload fields so it influences rank without polluting the embedding text.

Compared with PyPI.org search

Typical registry search

  • Strong on exact names and known keywords
  • Struggles when the query is a use-case, not a title
  • Little visibility into “is this still maintained?”

SARR

  • Matches intent in embedding space
  • Handles descriptive queries without exact lexical overlap
  • Surfaces better-maintained, more adopted options when relevance is close

Try “text to speech” or “async HTTP client with retries” on the search page. PyPI.org often ranks packages whose names contain the query words (including mismatched descriptions). SARR can surface a widely used library such as google-cloud-texttospeech even when the name is not a literal copy of the query — and can also over-retrieve near-misses such as speech-to-text vs text-to-speech.

Models and systems choices

The MVP uses a compact bi-encoder (BAAI/bge-small-en-v1.5, 384 dimensions) so indexing ~168k documents on a Colab T4 stays practical. ETL embeds the corpus with PyTorch / sentence-transformers. The Lambda image exports those weights to ONNX at build time so query embedding on CPU stays well under API Gateway’s 30s client wait. Reranking uses cross-encoder/ms-marco-MiniLM-L-6-v2 as ONNX on the retrieved shortlist rather than scoring the whole corpus — cheap recall, then selective precision.

Serving keeps the heavy lift out of the request path: corpus embeddings are precomputed. Each hosted request only runs small ONNX graphs for the query (and the cross-encoder when rerank is on), hits Qdrant, and blends scores. The same FastAPI app runs locally (sentence-transformers when no ONNX graph is present) and on Lambda (ONNX Runtime, no PyTorch), with shared schemas and document formatting between ETL and search.

What “fast enough” looks like today

Quote server took_ms for serving quality. Quote client RTT plus location for what a browser feels. Cold start is separate — do not fold it into p50 / p95 / p99.

  • Full corpus load: 167,619 packages (PyTorch embed + Qdrant upsert on a Colab T4).
  • Cold Lambda: about 5 s without rerank, about 16 s with rerank (loads ONNX sessions).
  • Warm, rerank=false: server p50 18 ms, p99 30 ms. Warm, rerank=true: p50 176 ms, p99 270 ms (~160 ms extra for the cross-encoder; a typical UI call is ~200–230 ms).
  • Warm stages: query embed ~7 ms, Qdrant ~9–11 ms (p50). Client RTT from this measurement was p50 ~122 ms (no rerank) and ~276 ms (rerank), including the path to us-east-1.

To reproduce: python3 scripts/measure_latency.py --url $SARR_API_URL --n 50 (15 Aug 2026: 1 warmup + 50 sequential mixed queries). Compare took_ms (server) with curl’s total time (client).
