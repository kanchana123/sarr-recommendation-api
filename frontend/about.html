How SARR finds packages

Embeddings, vector search, optional rerank, and an optional Gemini top-3 grounded in retrieved package descriptions.

The problem

Package registries are easy to search when you already know a name. They are harder when you only know the job: an HTTP client, a dataframe tool, something for retries. Keyword indexes reward exact tokens; they under-serve descriptive queries and rarely encode whether a project is widely used or still maintained.

SARR (Semantic Artifacts Retrieval and Ranking) indexes PyPI packages as semantic documents and returns a ranked list for natural-language queries. The live demo covers 167,619 packages from public Libraries.io metadata joined with repository signals. That dump is an MVP corpus — the newest release timestamp in this slice is from December 2018 — so ranking features are strong, while freshness is a known next step.

System design

Indexing is a rare GPU job (Colab, PyTorch). Serving only embeds the query, retrieves neighbors from Qdrant, optionally reranks, and blends in adoption and recency. If you check LLM, a second path asks Vertex Gemini for a grounded top-3 from those retrieved packages only. On Lambda both the bi-encoder and the cross-encoder run as ONNX — no PyTorch import on the request path. Both paths share the same BAAI/bge-small-en-v1.5 checkpoint and document format.

End-to-end path

  1. Index offline. A GPU batch job pulls PyPI rows from BigQuery, builds a structured text document per package, embeds it with a PyTorch bi-encoder, and upserts vectors plus metadata into Qdrant. Runs are watermarked so a disconnect can resume without duplicating points.
  2. Encode the query online. The same embedding checkpoint used at index time maps your search string into the same 384-d space. Hosted Lambda runs a baked ONNX graph; local dev can still use sentence-transformers when no ONNX files are present.
  3. Retrieve neighbors. Approximate nearest-neighbor search returns the closest packages by cosine similarity over the full collection.
  4. Refine when needed. If you check Rerank, the UI sends rerank: true and an ONNX MiniLM cross-encoder rescores the short top‑k list. No PyTorch import on Lambda. This checkbox does not call Gemini.
  5. Blend for usefulness. The final score mixes semantic relevance with adoption (stars, dependents, SourceRank) and release recency. Popularity stays in structured payload fields so it influences rank without polluting the embedding text.
  6. Grounded recommendations (optional). If you check LLM, the UI calls POST /v1/rag. Gemini writes a top-3 from the retrieved names and descriptions only. Packages not in that set are dropped. If generation fails, the ranked list is still the result. Leave LLM unchecked for search without an LLM call.

Grounded RAG (what shipped)

Search and generation are separate. Classic search still uses POST /v1/search. Checking LLM on the demo calls POST /v1/rag and streams Server-Sent Events. Checking Rerank only runs the ONNX cross-encoder; it does not call Gemini.

  1. Retrieve 50 neighbors from Qdrant (same bi-encoder as search).
  2. If Rerank is on, the MiniLM cross-encoder scores those 50; otherwise ranking uses cosine plus the popularity/recency blend. The API keeps the top 8 for the prompt.
  3. Emit ranked_list immediately. That list is a complete result if Gemini is slow or fails.
  4. Vertex Gemini (gemini-2.5-flash-lite, fallback gemini-2.5-flash) sees only package name and description. It returns JSON with exactly three package, reason, and cited_snippet fields.
  5. The backend drops any package not in the eight retrieved names, then emits llm_done (or llm_error). The UI marks a Gemini icon on that block so generated text is distinct from ranked hits.

Generation needs GCP_PROJECT_ID and Vertex billing. API Gateway HTTP APIs do not stream SSE well, so this path is meant for local FastAPI or Cloud Run. A labeled eval set (precision@k, citation accuracy, faithfulness) is still future work — not part of the serving stack above.

Compared with PyPI.org search

Typical registry search

  • Strong on exact names and known keywords
  • Struggles when the query is a use-case, not a title
  • Little visibility into “is this still maintained?”

SARR

  • Matches intent in embedding space
  • Handles descriptive queries without exact lexical overlap
  • Surfaces better-maintained, more adopted options when relevance is close
  • Optional Gemini top-3, cited from retrieved descriptions only

Try “text to speech” or “async HTTP client with retries” on the search page. PyPI.org often ranks packages whose names contain the query words (including mismatched descriptions). SARR can surface a widely used library such as google-cloud-texttospeech even when the name is not a literal copy of the query — and can also over-retrieve near-misses such as speech-to-text vs text-to-speech.

Models and systems choices

The MVP uses a compact bi-encoder (BAAI/bge-small-en-v1.5, 384 dimensions) so indexing ~168k documents on a Colab T4 stays practical. ETL embeds the corpus with PyTorch / sentence-transformers. The Lambda image exports those weights to ONNX at build time so query embedding on CPU stays well under API Gateway’s 30s client wait. Reranking uses cross-encoder/ms-marco-MiniLM-L-6-v2 as ONNX on the retrieved shortlist rather than scoring the whole corpus — cheap recall, then selective precision.

Serving keeps the heavy lift out of the request path: corpus embeddings are precomputed. Each hosted search request only runs small ONNX graphs for the query (and the cross-encoder when rerank is on), hits Qdrant, and blends scores. Gemini runs only when the caller uses /v1/rag (the demo LLM checkbox). The same FastAPI app runs locally (sentence-transformers when no ONNX graph is present) and on Lambda (ONNX Runtime, no PyTorch), with shared schemas and document formatting between ETL and search.

What “fast enough” looks like today

Quote server took_ms for serving quality. Quote client RTT plus location for what a browser feels. Cold start is separate — do not fold it into p50 / p95 / p99.

  • Full corpus load: 167,619 packages (PyTorch embed + Qdrant upsert on a Colab T4).
  • Cold Lambda: about 5 s without rerank, about 16 s with rerank (loads ONNX sessions).
  • Warm, rerank=false: server p50 18 ms, p95 65 ms, p99 67 ms. Warm, rerank=true: p50 172 ms, p95 257 ms (~154 ms extra for the cross-encoder; client p50 ~271 ms from this region).
  • Local RAG (warm, LLM + rerank on): ranked list 472 ms, Gemini top-3 1.05 s (llm_ms) for async HTTP client.
  • Hosted RAG (warm, LLM + rerank on Lambda): ranked list ~350–520 ms server took_ms, Gemini ~650 ms–1.2 s (llm_ms). API Gateway may deliver SSE in one block rather than streaming incrementally.

To reproduce search latency: python3 scripts/measure_latency.py --url $SARR_API_URL --n 50 (20 Aug 2026: 1 warmup + 50 sequential mixed queries on the live API). For rerank, warm up once then add --rerank --skip-warmup. Compare took_ms (server) with curl’s total time (client).

Stack at a glance

  • BigQuery → sentence-transformers / PyTorch → Qdrant Cloud
  • FastAPI + Pydantic for the search contract; Mangum on Lambda
  • ONNX Runtime for hosted query embeddings and rerank (no PyTorch import)
  • POST /v1/rag + SSE: retrieve 50 → top 8 → citation-checked Gemini top-3 (demo LLM checkbox)
  • Vertex Gemini (gemini-2.5-flash-lite, fallback gemini-2.5-flash) on GCP; service account in AWS Secrets Manager on Lambda
  • MCP stdio server (python -m sarr.mcp.server): search_packages, recommend_packages (RAG SSE → JSON), health
  • Vite demo (Search, How it works, Contact)
  • Automated unit tests and lint in CI
